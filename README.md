# Event Loop Lab

Интерактивная демонстрация для доклада **«Event Loop: как избежать блокировки интерфейса»**. Один детерминированный CPU-алгоритм выполняется четырьмя способами; зритель наблюдает JavaScript-индикатор, нажимает кнопку отклика и сравнивает реальные измерения.

HTML, CSS, нативный DOM API и JavaScript ES-модули. В приложении нет UI-фреймворков и runtime-зависимостей. Vite нужен только для разработки и сборки, Playwright — для браузерных проверок. Шрифты системные, все ресурсы локальные: после установки зависимостей сеть для демонстрации не нужна.

## Запуск

Проверено с Node.js **24.19.0** и npm **11.17.0**. Рекомендуется Node.js 24.

```bash
npm ci
npm run dev -- --port 5173 --strictPort
```

Открыть **http://127.0.0.1:5173/**. Для остановки сервера — `Ctrl+C`.

Production-сборка и её локальный просмотр:

```bash
npm run build
npm run preview -- --port 4173 --strictPort
```

Открыть **http://127.0.0.1:4173/**. Статические файлы находятся в `dist/`; их можно разместить на HTTP(S)-хостинге. Сервер приложения и облачные сервисы не требуются. При размещении в подпапке задайте соответствующий `base` Vite при сборке, например `npm run build -- --base=/event-loop/`.

**Не открывайте `index.html` через `file://`:** для ES-модулей и модульного Worker нужен HTTP(S)-сервер. Используйте актуальный браузер с поддержкой module Workers, `AbortSignal.throwIfAborted()` и CSS `color-mix()`. Автоматически проверен Chromium; Safari и Firefox отдельно не проверялись.

## Как пользоваться

1. Выберите режим и нагрузку. Для первого выступления оставьте **8 млн** элементов.
2. Запустите эксперимент и нажимайте «Проверить отклик». Следите за вращением точки, счётчиком кадров и прогрессом.
3. Повторите с другой стратегией при **том же количестве элементов**.
4. Сравните общее время, максимальный интервал кадров и контрольную сумму.
5. Раскройте «Разобрать подход и посмотреть код», чтобы объяснить механизм.

Порционный расчёт и Worker можно остановить. В синхронном режиме и цепочке микрозадач остановка недоступна: её обработчик сам не получит управление. Запуск, выбор настроек, повтор и сброс заблокированы на время опыта, поэтому эксперименты не пересекаются. Отмена и ошибки освобождают управление без перезагрузки.

Каждый запуск остаётся отдельной строкой. Кнопка ↻ в строке повторяет её режим и нагрузку. «Сбросить» очищает историю, эталоны, счётчик нажатий и метрики. История хранится в памяти текущей страницы; перезагрузка также её очищает.

Схема на странице — **иллюстрация модели выполнения, не трассировка планировщика**. Ширина блоков не связана с измеренной длительностью. Код в раскрывающемся блоке показывает суть стратегии; обработка отмены, ошибок и часть измерительных обвязок опущены для читаемости. Полная реализация — в исходниках.

## Одна задача, четыре режима

### Алгоритм

Для каждого индекса от `0` до `N − 1` создаётся 32-битное значение. Оно проходит ровно **128 раундов** умножений `Math.imul`, XOR, циклических сдвигов и сложений, затем включается в последовательную 32-битную контрольную сумму. Это детерминированное преобразование чисел, а не криптографический алгоритм.

Вход вычисляется по индексу, поэтому нет большого массива и блокирующей подготовки данных. Память расчёта — O(1), работа — O(N × 128). Во всех стратегиях вызывается одна и та же `processUntil()`; порядок обработки и накопления суммы одинаков. Порции меняют только границы вызовов. Вывод суммы и её использование в сравнении делают вычисленный результат наблюдаемым: работа не является бессмысленным циклом с неиспользуемым выходом.

Первый успешный запуск каждой нагрузки становится **эталоном серии**, последующие сравниваются с ним. Несовпадение переводит запуск в ошибку. Частичные результаты после отмены не сравниваются. Значения результатов в интерфейсе не заданы заранее и не генерируются случайно. Совпадение 32-битной суммы полезно для проверки этой демонстрации, но не является математическим доказательством отсутствия коллизий. Модульные тесты дополнительно сравнивают алгоритм с независимой реализацией на `BigInt`.

### 1. Синхронно

Один вызов `processUntil(work, total)` выполняет весь объём в главном потоке. Пока задача не завершится, не выполняются обработчики ввода и следующий rAF. Прогресс становится видимым после расчёта. Простой подход с небольшими накладными расходами подходит для короткой работы.

Перед стартом приложение обновляет статус, даёт браузеру две возможности отрисовки через rAF и начинает расчёт отдельной задачей таймера. Это позволяет увидеть состояние «Выполняется» до блокировки. Такая подготовительная пауза не включена во время опыта.

### 2. Async / await через микрозадачи

По 8192 элемента обрабатываются между `await Promise.resolve()`. Продолжения выполняются как микрозадачи. Микрозадачный checkpoint опустошает очередь, включая новые добавленные микрозадачи; длинная цепочка откладывает переход к следующей задаче и возможности обновления отрисовки. Изменение DOM-прогресса не означает, что браузер уже показал его зрителю.

`async` сам по себе не создаёт поток. Этот конкретный пример демонстрирует ошибку с **уже разрешённым Promise**; ожидание действительно незавершённого I/O может вернуть управление циклу событий. См. [модель Event Loop в HTML Standard](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model).

### 3. Порциями

Порция занимает ориентировочно **7 мс**. Время проверяется после каждых 256 элементов; поэтому бюджет не является жёстким deadline и может быть превышен на длительность одного блока или задержку ОС. Между незавершёнными порциями используется `setTimeout(..., 0)` — отдельная задача, а не микрозадача.

Браузер получает возможность обработать ввод и кадр, но кадр не гарантируется после каждой порции. Нулевая задержка таймера не означает немедленный запуск. Полная обработка обычно дольше из-за ожидания таймеров и обслуживания интерфейса. Отмена проверяется между порциями.

### 4. Web Worker

Модульный Worker импортирует тот же алгоритм и выполняет основную нагрузку вне главного потока. Массивы не пересылаются: на вход идёт только количество элементов. Прогресс отправляется с интервалом не менее примерно **80 мс** (около 12 сообщений в секунду), отдельно отправляется итоговый результат.

Главный поток обновляет DOM по сообщениям. После завершения, ошибки или отмены вызывается `worker.terminate()`; сам Worker также закрывается после отправки результата. Отмена не требует, чтобы занятый Worker сначала обработал сообщение. Ошибки создания, загрузки, исполнения и десериализации сообщений обрабатываются.

Worker не имеет доступа к DOM и не гарантирует ускорения одной последовательной задачи. Создание потока, сообщения и конкуренция за CPU имеют накладные расходы. См. [Web Workers в HTML Standard](https://html.spec.whatwg.org/multipage/workers.html#introduction-15).

## Выбор нагрузки

| Уровень     |   Элементы | Раунды вычислений | Когда использовать                                                         |
| ----------- | ---------: | ----------------: | -------------------------------------------------------------------------- |
| Лёгкая      |  1 000 000 |       128 000 000 | Быстрая проверка, менее мощное устройство                                  |
| Для доклада |  8 000 000 |     1 024 000 000 | Основная демонстрация; цель — примерно 2–4 с синхронной работы             |
| Тяжёлая     | 16 000 000 |     2 048 000 000 | Если на вашем устройстве пауза слишком короткая                            |
| Предельная  | 24 000 000 |     3 072 000 000 | Усиленная демонстрация; синхронный режим может надолго заморозить страницу |

Это **число реальных операций**, а не обещание длительности. Автокалибровки по времени нет: она могла бы незаметно менять объём сравниваемой работы. Перед докладом сделайте пробный запуск. Уменьшите нагрузку, если синхронная пауза слишком долгая; увеличьте, если она едва заметна. Не меняйте нагрузку внутри сравниваемой серии.

## Что именно измеряется

| Показатель                   | Методика                                                                                                                                            |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Общее время                  | `performance.now()` от начала выбранной стратегии до получения её результата. Для Worker включены создание, загрузка и доставка итогового сообщения |
| Вычисления                   | Сумма длительностей вычислительных участков по `performance.now()`; в Worker измеряется внутри Worker                                               |
| Паузы и накладные расходы    | Разность общего времени и вычислительных участков, ограниченная снизу нулём из-за возможного округления таймера                                     |
| Максимальный интервал кадров | Максимальная разность `performance.now()` между соседними фактическими вызовами rAF за период наблюдения                                            |
| Счётчик кадров в круге       | Число выполненных rAF после загрузки или сброса; сама точка тоже перемещается из rAF через JavaScript                                               |
| Кадры в подписи результата   | Число rAF, попавших в период наблюдения конкретного опыта                                                                                           |

Наблюдение начинается непосредственно перед стратегией. Первый интервал может начинаться в предыдущем rAF перед стартом, а заканчивается наблюдение **только в первом rAF после получения результата**. Следовательно, длительная синхронная работа, во время которой монитор не мог выполняться, всё равно попадёт в максимум. Ожидание этого последнего кадра не добавляется к общему времени вычислительной задачи.

Оценки в таблице условные: **до 50 мс включительно** — «Короткие интервалы», **больше 50 до 200 мс** — «Заметная пауза», **больше 200 мс** — «Долгая пауза». Они характеризуют наблюдение за кадрами, а не доказывают конкретную причину задержки. Для скрывавшейся вкладки вместо оценки выводится предупреждение.

### Ограничения интерпретации

- Интервал rAF — не INP, не Long Tasks API, не измерение длительности конкретного обработчика ввода и не точная длина блокировки. В него входит обычное ожидание кадра и возможная работа браузера/ОС.
- «Вычисления» — прошедшее время внутри участков кода, **не аппаратное CPU time**. Вытеснение ОС, JIT и сборка мусора могут входить в него. Разность времён не изолирует стоимость только `postMessage` или только таймеров.
- rAF показывает выполнение JavaScript callback, а не подтверждённый вывод пикселей на монитор. CSS-анимация не используется как свидетельство отзывчивости.
- Частота монитора, энергосбережение, прогрев JIT, DevTools, расширения, фоновые задачи, запись экрана и тепловой режим влияют на результаты. Порядок запусков тоже может влиять; повторите серию в другом порядке.
- rAF обычно приостанавливается в скрытой вкладке. Приложение помечает замеченный уход в фон; если вычисление завершилось в фоне, финализация ждёт следующего кадра после возвращения. Проводите опыт в активной вкладке. См. [описание requestAnimationFrame на MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame).
- Worker уменьшает нагрузку главного потока, но на перегруженном устройстве не гарантирует отсутствие задержек UI.
- После отмены отображается только известный прогресс, а длительности полного расчёта, накладных расходов и итоговая сумма отсутствуют. Отменённые/ошибочные запуски не используются как эталоны.
- Наблюдение и обновления UI сами имеют небольшую стоимость. Это учебный эксперимент, а не лабораторный бенчмарк браузерного движка.

## Проверки

```bash
# Алгоритм, независимый эталон, разбиение и отмена
npm test

# Первый раз — установить официальный тестовый Chromium
npx playwright install chromium

# Проверяется именно production-сборка, включая собранный Worker
npm run build
npm run test:browser
```

Playwright сам запускает `vite preview` на порту 4173 и завершает принадлежащий ему сервер после проверок. Тесты выполняются одним worker-процессом: параллельные CPU-эксперименты исказили бы измерения. Порт должен быть свободен либо занят preview-сервером этой же сборки. На Linux CI для Chromium могут потребоваться системные библиотеки (`npx playwright install --with-deps chromium`).

Браузерные проверки охватывают совпадение контрольных сумм всех четырёх стратегий, попадание блокировки в максимальный интервал, реальные клики во время chunking/Worker, живой прогресс, сообщения и завершение Worker, запрет параллельных запусков, отмену, повтор, сброс, разные нагрузки, восстановление после ошибки и мобильную вёрстку. Ошибки страницы и консоли собираются во время основной серии. Числа тестов берутся из реальных результатов приложения, а не подменяются.

Снимки десктопной и мобильной страниц сохраняются в `test-results/`. При падении также сохраняется trace. Результат проверенного запуска и ограничения среды описаны в [docs/verification.md](docs/verification.md).
